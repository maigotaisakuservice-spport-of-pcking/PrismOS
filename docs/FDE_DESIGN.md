# 全ディスク暗号化 (FDE) 設計

状態: **本体組み込みまで実装済み (2026-11-23)**。起動前
パスフレーズ解除 + ブロック層暗号シム + ジャーナル付き
インプレース移行 (有効化/無効化とも) が入り、専用 QEMU
テスト (scripts/fde-test.py、全 7 段: 有効化 → ロック →
パスフレーズ解除 → リカバリキー解除 → 回復モード →
無効化 → 平文回帰) が合格している。対象はデータ区画
(PRISMFS) のセクタ単位暗号化。起動区画 (FAT16、カーネルと
Limine) はブートローダが読むため平文のままにする —
これは LUKS 等でも同じ割り切りである。

実装時の判断・乖離 (正直な記録):
- ヘッダセクタはデータ領域の相対セクタ 0 に置く。全体配置
  ではこのセクタは MBR そのもので、diskfs_is_formatted が
  パーティション表 (446〜) と署名 (510-511) を検査する
  ため、ヘッダ書き込みは読み直し + 占有域 ([0..276)) の
  み重ねる方式にし、MBR 末尾を保存する。無効化時は占有域
  だけを消すので MBR がそのまま復元される。
- §2 で触れた「ヘッダセクタの空き領域に言語・タイム
  ゾーンを平文で置く」は未実装 (ログイン前の最小設定は
  従来どおり暗号化区画内の平文ファイル経由)。
- §5 の「ファイル単位暗号化のファイルは先に平文に戻して
  から移行」は行わない: ファイル単位の暗号文がそのまま
  セクタ暗号の下に重なる形で移行し、読み出し時はセクタ
  復号 → ファイル復号の順で従来どおり復元される (二重に
  暗号化されるが読み書きは一貫する)。
- 組み込み作業中に見つけた実バグ 2 件も同時修正:
  (1) crypto_kdf が固定 64 バイトバッファを使うため、
  ソルト 16 バイト + 17 文字以上のパスフレーズでスタック
  を溢れていた (PIN 上限 16 文字のため未発現だったが、
  24 文字のリカバリキーで #GP を確認)。ストリーミング
  化し、既存 PIN の導出結果が変わらないことを既知答
  テストで固定した。(2) ATA の BSY/DRQ 待ちが 100 万回
  固定で、CPU を絞られた仮想環境では正常な書き込みでも
  時間切れした (移行の連続書き込みで再現)。上限を
  3000 万回へ緩和 (ERR 時は即時復帰のため異常系は不変)。

## 1. 現在の仕組みと、その限界

現在はファイル単位の暗号化 (shell/diskfs.c + kernel/persist.c):

- PIN から `crypto_kdf` で鍵を作り、ファイルごとに
  AES-256-CTR で暗号化して保存する。IV は鍵とカウンタから生成。
- `.account` と `settings.txt` はログイン前に読む必要があるため
  **平文**で保存される (例外扱い)。
- 限界:
  - ファイル名・サイズ・更新時刻 (diskfs の表) は平文で見える。
  - `.account` (ソルトと反復ハッシュ) が平文で露出する。
    オフライン総当たりへの耐性は反復回数だけが頼り。
  - 削除したファイルのデータ残骸は暗号化の対象外になり得る。

## 2. 鍵の階層 (ラップ方式)

```
パスフレーズ ──crypto_kdf(salt, 反復)──> KEK
マスター鍵 (乱数 32B) ──AES-256-CTR(KEK, iv)──> 包まれた鍵
完全性: HMAC-SHA-256(KEK, iv || 包まれた鍵) 先頭 16B
```

- マスター鍵はインストール時に乱数で生成し、ディスク自体の
  暗号化はこの鍵だけで行う。パスフレーズ変更は包み直しだけで
  済み、データの再暗号化は不要。
- 包んだ鍵・salt・iv・MAC はデータ区画の先頭セクタに置く
  ヘッダ (magic `PRISMFK1`、形式は kernel/fde.h) に入れる。
- **`.account` の所在問題はこれで消える**: 起動前に必要なのは
  ヘッダセクタだけで、アカウントファイルは暗号化された区画の
  中に置ける。ログイン画面の言語など秘密でない最小限の設定は
  ヘッダセクタの空き領域に平文で置く (言語・タイムゾーンのみ)。
- 鍵スロットは 2 つ用意する: スロット0 = 利用者のパスフレーズ、
  スロット1 = 管理者のリカバリキー (仕様の「管理者保持の
  リカバリキー」)。どちらでも同じマスター鍵が開く。

この包む/開く処理は **kernel/fde.c として実装済み**で、
ホストテスト (tests/test_fde.c、17 件) で往復・誤パスフレーズ
拒否・改ざん検出を確認している。既存の保存経路には接続して
いない。

## 3. セクタ暗号化の方式

ブロック層 (kernel/block.c) と persist の間に暗号シムを挟む:

- 書き込み: セクタ番号とブロック位置から IV を決め、
  AES-256-CTR で暗号化してから下のデバイスへ。
  `IV = SHA-256(マスター鍵 || LBA || セクタ内ブロック番号)` の
  先頭 16 バイト (persist.c の make_iv と同じ発想で、IV を
  保存せずに済む)。
- 読み込み: 逆向きに復号。
- 正直な注意: この方式は同じ平文を同じセクタに書き直すと
  同じ暗号文になる (XTS のような拡散がない)。v1 の割り切り
  として文書化し、AES-XTS の実装が入った時点で置き換える。
- 対象はデータ区画の LBA 範囲のみ。persist.c が MBR から
  決める base_lba / セクタ数をそのまま使う。

## 4. 起動フロー

1. カーネルがブロックデバイスと MBR を読み、データ区画の
   ヘッダセクタを読む。magic が無ければ FDE 無効として従来通り。
2. フレームバッファとシリアルにパスフレーズを聞く
   (現在の PIN ログイン画面を前倒しする形)。入力は伏せ字。
3. `fde_unwrap_key` で開く。MAC が合わなければ間違い。
   3 回失敗したらディスク無しで起動する (現在のロック状態と
   同じ扱い。シェルは使えるがファイルは読めない)。
4. 開けたらマスター鍵をメモリにだけ置き、暗号シムを有効化
   してから通常の persist 読み込みに進む。以後のログイン
   (アカウントの PIN) は従来通り区画の中で行う。

## 5. 移行 (既存ディスク)

- `fde enable` (管理者) で開始: マスター鍵生成 → ヘッダを
  書き → セクタを 1 つずつ「読んで暗号化して書き戻す」。
- 途中終了に備え、進捗セクタ番号をジャーナル領域に記録し、
  起動時に未完了なら再開する。ファイル単位暗号化で書かれた
  ファイルは、先にログイン状態で平文に戻してから移行する
  (二重暗号化を避ける)。
- 移行が終わるまでは旧経路でも読める状態を保つ。

## 6. 組み込み時の経緯と受け入れ結果

- 当初 (2026-11-22) は起動順序の変更がインストーラ・
  更新・回復の経路の根幹に触れるため、部品と設計までに
  留めた。2026-11-23 の第 3 セッションで組み込みを実施。
- 受け入れ条件だった既存 QEMU テスト (disk-boot /
  install / installer / login / recovery / update /
  kernel-update / desktop) は全て回帰合格し、FDE 固有の
  ケースは専用の fde-test が担う (回復モードと FDE の
  併用もその中で検証済み)。
- 移行が途中で止まった場合はジャーナルから再開する。
  実際に書き込み失敗で中断したディスクで再開が完了する
  ことも確認した。ジャーナルは毎セクタ記録する (間隔を
  空けると「処理済みだが未記録」のセクタが再開時に
  二重暗号化されて失われるため)。これでエラー復帰時は
  完全に一貫する。残る窓はハードな電源断が「データ
  書き込み完了〜ジャーナル書き込み」の間に起きた場合の
  最大 1 セクタだけで、その 1 セクタを含むファイルは
  失われ得る。完全な電源断耐性 (コピーオンライト等) は
  今後の課題として正直に残す。
