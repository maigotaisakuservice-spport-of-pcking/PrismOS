## 観点1：ビルド再現性とサプライチェーン

### 新規発見
- **スナップショット時点で `make test` が test_tls のリンクで落ちる**（`kernel/tls.c:938,1108` が `entropy_reseed`/`entropy_add` を呼ぶが、`Makefile:284-290` の test_tls ルールは tests/test_tls.c・tls.c・crypto.c のみで security.c/entropy_hw.c をリンクしていない）。カーネル本体はリンクでき、フルビルドは成功した。開発担当のエントロピー修正の途中状態を拾った可能性が高いので、本体ツリーでの再確認が必要。
- **`make clean` が不完全**（`Makefile:764-767`）。消えるのは obj・kernel.elf・prismos.iso・iso_root・test_shell・test_memory・boot.log のみで、obj32・ARMオブジェクト・他のテストバイナリ群・32bit/dualboot ISO・qcow2・live-usb img 等が残る。パターンルール（`Makefile:100-102`）にヘッダ依存追跡（-MMD 等）がないことと組み合わさると、「clean したのに古いオブジェクトでリンク」が 32bit/ARM/テスト側で起こり得る。
- **Limine tarball の SHA-256 が検証されていない**（`Makefile:49-57`）。版とタグ（v8.3.2-binary）は固定され、コメントに観測ハッシュ `abe24c…` があるが「参考値」で、ダウンロード後の照合処理がない。整合性保証は HTTPS のみ。
- **`.github/workflows/build-variants.yml` の成果物パスが実ファイル名と不一致**。live-usb ジョブは `build/boot-live-usb.log`、vm ジョブは `build/boot-vm.log` を指定するが、実スクリプトが書くのは `build/live-usb.log`（`scripts/live-usb-test.py:35`）と `build/vm.log`（`scripts/vm-test.py:31`）。upload-artifact v4 は該当ファイルなしでも警告のみでジョブは失敗しないため、CI 失敗時に診断ログが黙って欠ける。

### 問題なし（確認した範囲）

## 観点2：割り込み・並行性・タイミング

### 新規発見
- **PIT チャンネル0の分周比が復元されない**。`kernel/sandbox.c:224-228` の `sandbox_watchdog_start` が分周を 11932（約100Hz）に書き換え、`sandbox_watchdog_stop`（同:236-245）は IRQ0 マスクと IDT ゲートだけ戻して分周を戻さない。一方 `kernel/speaker.c:20-37` の `speaker_wait_ticks` はカウンタ差分を 65536 折り返し前提で測る。よって互換ゲストを1回でも実行した後は、PIT 基準の待ち（UHCI 転送の 200ms 待ち `kernel/uhci.c:442`、スピーカー音長、音楽再生の待ち等）が最大約5.5倍短く・不規則になる。実在するタイミング劣化バグ。
- **`kernel/mouse.c:248-266` の `mouse_poll`**：`mouse_changed` を落としてから蓄積量を読んでゼロ化するため、間に IRQ12 が入ると動きの取りこぼし、または dx=0 の空イベントが起こり得る。実害は表示品質のみ。
- **`entropy_add` の競合**：IRQ 文脈（`kernel/keyboard.c:286`、`kernel/mouse.c:201`）からも呼ばれる非原子的な read-modify-write で、プール更新の取りこぼしは起こり得る。ただしメモリ破壊にはならず、影響はエントロピー品質のみ（この評価は推測を含む）。

### 問題なし
- キーボード IRQ ハンドラは軽量（ポート読み・変換・リング投入・EOI のみ、割り込み中のシリアル出力なし）。リングバッファは volatile + head（IRQ）/tail（メイン）分離が正しい。`uhci_input_poll` は非ブロッキングでメイン文脈からのみ呼ばれる。

## 観点3：電源断・途中失敗時のデータ保全

### 新規発見
- **通常ファイルにチェックサムがなく、上書き途中の電源断を検出できない**。`shell/diskfs.h:66-76` のエントリは name/size/start_sector/iv のみ（チェックサムはスナップショット専用、`shell/diskfs.c:504,583`）。`diskfs_write_file` はデータ→表の順で書く（順序自体は適切）が、既存ファイルの上書き中に落ちると、旧サイズのまま前半だけ新しい内容のファイルが残り、検出手段がない。暗号化ファイルでは復号結果が化けるだけで同様に無検出。
- **更新適用の最終同期が途中で落ちると新旧混在が残り、起動時に検出されない**。`kernel/shell.c:2026-` の `update_apply_manifest` は検証済みファイルを RAM 上の VFS に書いて最後に一括同期する設計で、ダウンロード中の電源断ではディスクは無事。しかし最終 sync の途中で落ちた場合は混在状態のまま次回起動し、中断を示すマーカーも自動検出もない。pre-update スナップショットはあるので回復モードから手動で戻せるが、自動ではない。

### 問題なし
- カーネル更新の入れ替えは `fat16_swap_entries` による単一セクタ書き込みで原子的（`kernel/shell.c:1996-2003`）。設定ファイルが壊れても `settings_parse` が寛容で起動不能にはならない（観点4のファズでも確認）。

## 観点6：ライセンス・帰属

### 新規発見
- **配布物（ISO）の中に第三者ライセンスが一切入っていない**。ISO ルール（`Makefile:170-186`）が iso_root に入れるのはカーネル・limine.conf・Limine バイナリ・BOOTX64.EFI のみ。Noto 由来グリフは OFL 1.1 でライセンス文の同梱が条件だが、グリフが埋め込まれたカーネルを含む ISO にも OS 内の表示にもライセンス文がない。Limine 本体（BSD 系）分も同様。リポジトリ側は `assets/NotoSansCJK-LICENSE.txt` と `kernel/jfont_data.c`/`jfont.h` の帰属コメントがあり概ね良好で、不足は配布物側。
- **ルートの LICENSE は全体を MIT としているが、OFL フォント・BSD の Limine 等を含むため第三者通知（NOTICE 相当）がなく実態と完全には一致しない**。Canva 素材は帰属表示義務がない（既知の利用条件通り）ので不足は主に OFL と BSD 分。

### 問題なし
- `kernel/limine.h` は BSD Zero Clause のヘッダを保持している。
